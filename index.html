BloomFilter

Bloom filters are space-efficient probabilistic data structures used to test whether an element is a member of a set or not. Discovered by Burton Howard Bloom in 1970

The explanation of bloomfilter is pretty standard: take an array of m bits, and for up to n different elements, either test or set k bits using positions chosen using hash functions. If all bits are set, the element probably already exists, with a false positive rate of p; if any of the bits are not set, the element certainly does not exist.

Application of BloomFilter in database management systems:

The DBMS is a complex piece of software and have many componenets to control memory, disk reads, concurrency, etc.

In any production database like MySQL, PostgreSQL implements indexing with B+ Tree because it gives the power to the dbms to query for range scans with minimum disk I/O reads and every dbms wants to be fast in this section of the query for faster results.

But there is a little time consuming and more disk I/O operations are possible even though b+ tree is implemented as i said dbms wants to be fast so the problem is that
Every node in b+ tree is a page and pages are managed(fetched from disk to memory) in Buffer Pool Manager. Consider dbms search for index key X then the search operation ahve to traverse from root to leaf inorder to get the truth of existence. If the key is present return the result if not we already done many disk operations(root to leaf) for a "no existence" answer.

The inner node keys in a B+Tree cannot tell you whether a key exists in the index. You must always traverse to the leaf node.

To optimize this we have BloomFilters over index key. The same scenario with BloomFilter is that if dbms have to search index key X the search operation goes in bloomfilter if the key exists then it have to fetch the necessary page and if the key doesn't exist in bloomfilter it is definitely not in b+ index tree.

Hence, we saved some disk I/O and performance is boosted.

Tradeoffs using BloomFilter:
The key trade-off is false positives - some non-existent items may pass the check. However, Bloom Filters never produce false negatives, so correctness is never compromised.
In practice, this trade-off is acceptable because the cost of an occasional extra check is far lower than performing expensive operations for every request.

Bloomfilter depends on these factors:

  • an array of m bits

  • k: different hash functions count

  • p: false positive probability, between 0 and 1 (exclusive)

  • n: expected number of elements in bloomfilter

Calculation is based on following formulae:

  • Bits needed: m= ⌈ − n⋅ln⁡p (ln⁡2) 2 ⌉

  • Optimal hash functions: k= mn ⋅ln⁡2

  • False positive rate: p≈ (1− e − knm ) k

  • Expected number of elements in bloomfilter: n= ⌈ − m⋅ln⁡ (1− p1/k ) k ⌉
